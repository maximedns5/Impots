## 1. M2 / calibrate.py — build it, but as Branch-C infrastructure

The "near-identity on sex×age" argument is accepted as far as it goes — and it
was never the point of raking. Raking is joint: the value of keeping sex×age in
the margin set is not to move those margins but to *constrain* the adjustment
made to the others. And the +1.5 % ménages / −0.0 % individuals pair is not a
clean bill: at fixed persons, +1.5 % households means household size runs ~1.5 %
small — a composition skew, mild here, which is exactly what a household-type
margin corrects.

That said, the reconciliation table shows the A' vintage's real failures live in
income synthesis, not in weights, and D-016 rightly refuses to polish A'. So the
ruling is:

* **Build `calibrate.py` now**: margins-agnostic IPF raking, weight-ratio bounds
  [0.2, 5], convergence + bounds tests — per spec §4.3, ~80 lines. It is on the
  critical path of Branch C, not of A': ERFS arrives with weights calibrated to
  its own vintage year (2-3 years stale) and must be re-raked to simulation-year
  margins. Both branches need it; the Progedo waiting window is the natural slot.
* **Run it once on A'** with two margin sets — households by type (RP), and
  age-band × sex as drift constraints; no region margin (the EEC has no region,
  M0 §4.3). Record before/after for every reconciliation line in the report
  itself, whatever the direction. If the effect is as small as predicted, the
  report saying so is worth having; if AF or foyers move, better still.
* The income-mass scaling already done stays as-is for A' (it dies with ERFS
  anyway), and the wage-bill margin stays marked spent — D-014 already handles
  this correctly.

Log as **D-017**.

# Addendum — verdict on the knobs increment (D-033..D-042)

## Endorsed, with the phase's most important finding named

**D-042 is the deepest thing this project has learned about verification.** The
2026 refonte *replaced* the allègements structure, so writing an old child name
succeeded — `update()` created the node, and the D-007 read-back then confirmed
the value it had itself just written. A check that shares a write path with the
thing it checks can self-confirm; read-back guarded against wrong values, not
against writing into the void. The existence-check-before-write fix is right.
Two generalisations, ruled now:

* **`update()` may never create.** Any reform write targeting a node that does
  not exist at the reform's start date is an error by default — creation is a
  separate, explicit operation. This subsumes the existence check and closes
  the whole class, not the instance.
* **A verification is only as good as its causal independence.** Where
  possible, read-backs compare against an *independently constructed*
  expectation (the spec value, a fresh parameter resolution), not against
  whatever the write path now contains. Audit the other verify_* functions for
  the same shared-path pattern once; record what is found either way.

## The 17.7 bn / zero-cost bug gets a structural answer: double-entry (rule, log it)

`reform_cost` being household-side only was caught by the behavioural layer by
luck of adjacency. The structural guard is an **accounting identity asserted on
every reform run**: the deltas across sectors must balance — what households
and firms gain, the state loses, to stated tolerance. A reform that moves
labour cost by 17.7 bn with a public cost of exactly zero should die on the
identity, not wait for a reviewer. Cheap, vectorised, and it catches every
future knob whose cost wiring is incomplete on either side.

## The +107 % cliff finding becomes a runtime flag, not just a decision entry

The barème/+10 % vs cliffs/+107 % contrast upgrades D-015 from "level shift"
to "mis-shaped density", and it has a product consequence: compute, per reform,
the **share of mechanical yield concentrated in narrow wage bands** (households
within a small window of the instrument's thresholds). Above a threshold share,
the UI carries the specific caveat — *"this reform's yield turns on a narrow
wage band, where the synthetic distribution is least reliable (D-015); treat
the level as overstated until the ERFS population lands."* The backtest
measured the failure mode; the runtime should point at it whenever a user walks
into it.

## C4's resolution is exemplary

Bounds read from the tables, straddling zero because the paper's own
comparisons disagree, with the authors' "grande prudence" carried into the
parameter file. That is what "no detectable response" looks like when it is
sourced rather than assumed.

## The 23-minute suite — tier it before it compounds

Chiffrage cases that touch only IR/cotisation instruments do not need the
full benefits cascade: run them light-tier where the article's instruments
permit, and mark the genuinely full-tier ones. Split the suite with pytest
marks: a fast default gate (target < 5 min) and the full pass (nightly, or on
CI where minutes are cheap). Do not let local test pain create pressure to
skip runs — that is how green suites rot.

## Also worth keeping

Three of the five dead chiffrage cases failed on the *official record's*
verifiability, not on this repository. The Cour des comptes said exactly this
about chiffrage documentation in 2024; the project now holds receipts. That
paragraph belongs in whatever public methods page eventually ships.
