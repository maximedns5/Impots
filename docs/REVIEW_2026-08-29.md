## 1. M2 / calibrate.py — build it, but as Branch-C infrastructure

The "near-identity on sex×age" argument is accepted as far as it goes — and it
was never the point of raking. Raking is joint: the value of keeping sex×age in
the margin set is not to move those margins but to *constrain* the adjustment
made to the others. And the +1.5 % ménages / −0.0 % individuals pair is not a
clean bill: at fixed persons, +1.5 % households means household size runs ~1.5 %
small — a composition skew, mild here, which is exactly what a household-type
margin corrects.

That said, the reconciliation table shows the A' vintage's real failures live in
income synthesis, not in weights, and D-016 rightly refuses to polish A'. So the
ruling is:

* **Build `calibrate.py` now**: margins-agnostic IPF raking, weight-ratio bounds
  [0.2, 5], convergence + bounds tests — per spec §4.3, ~80 lines. It is on the
  critical path of Branch C, not of A': ERFS arrives with weights calibrated to
  its own vintage year (2-3 years stale) and must be re-raked to simulation-year
  margins. Both branches need it; the Progedo waiting window is the natural slot.
* **Run it once on A'** with two margin sets — households by type (RP), and
  age-band × sex as drift constraints; no region margin (the EEC has no region,
  M0 §4.3). Record before/after for every reconciliation line in the report
  itself, whatever the direction. If the effect is as small as predicted, the
  report saying so is worth having; if AF or foyers move, better still.
* The income-mass scaling already done stays as-is for A' (it dies with ERFS
  anyway), and the wage-bill margin stays marked spent — D-014 already handles
  this correctly.

Log as **D-017**.

## 2. Licence — AGPL-3.0-or-later, now

The analysis is correct and the recommendation is accepted, with one precision:
match upstream's exact expression, **AGPL-3.0-or-later** (openfisca-core and
openfisca-france are both "or-later"; taking "-only" would create pointless
friction against a future upstream move to v4). Split-tree is rejected —
maintenance overhead a solo project doesn't need, protecting a hosting option
this project doesn't want. And unlicensed-forever fails the project's founding
premise: a transparency tool nobody may legally run is a contradiction.

One argument the report undersold: for *this* project §13 is not a cost, it is
the thesis. The product's signature is showing its working; a licence under
which nobody can host a closed fork of the honesty machine is the licence that
matches the mission.

Do: `LICENSE` (AGPL-3.0-or-later text), README licence section (code AGPL;
data licensing independent — EEC Licence Ouverte with attribution, ERFS
non-redistributable per D-016), `pyproject.toml` licence field, close the
licence half of D-001.

**And settle D-001's other half in the same commit**, as the report suggested,
before any firm-package code exists: the Phase 2 firm package is developed
**in-repo, as an independent extension package following OpenFisca conventions**
(YAML dated parameters, openfisca-test-format YAML cases), AGPL like everything
else, structured so it can be *offered* upstream once it has substance (IS,
C3S, CFE encoded and tested) — but not gated on OpenFisca-org governance or
review latency, which the Phase 0 audit measured as thin. Contribution is the
goal; the fork-shaped start is the schedule. Log as **D-018**.

language model.)
