## 1. M2 / calibrate.py — build it, but as Branch-C infrastructure

The "near-identity on sex×age" argument is accepted as far as it goes — and it
was never the point of raking. Raking is joint: the value of keeping sex×age in
the margin set is not to move those margins but to *constrain* the adjustment
made to the others. And the +1.5 % ménages / −0.0 % individuals pair is not a
clean bill: at fixed persons, +1.5 % households means household size runs ~1.5 %
small — a composition skew, mild here, which is exactly what a household-type
margin corrects.

That said, the reconciliation table shows the A' vintage's real failures live in
income synthesis, not in weights, and D-016 rightly refuses to polish A'. So the
ruling is:

* **Build `calibrate.py` now**: margins-agnostic IPF raking, weight-ratio bounds
  [0.2, 5], convergence + bounds tests — per spec §4.3, ~80 lines. It is on the
  critical path of Branch C, not of A': ERFS arrives with weights calibrated to
  its own vintage year (2-3 years stale) and must be re-raked to simulation-year
  margins. Both branches need it; the Progedo waiting window is the natural slot.
* **Run it once on A'** with two margin sets — households by type (RP), and
  age-band × sex as drift constraints; no region margin (the EEC has no region,
  M0 §4.3). Record before/after for every reconciliation line in the report
  itself, whatever the direction. If the effect is as small as predicted, the
  report saying so is worth having; if AF or foyers move, better still.
* The income-mass scaling already done stays as-is for A' (it dies with ERFS
  anyway), and the wage-bill margin stays marked spent — D-014 already handles
  this correctly.

Log as **D-017**.

## 2. Licence — AGPL-3.0-or-later, now

The analysis is correct and the recommendation is accepted, with one precision:
match upstream's exact expression, **AGPL-3.0-or-later** (openfisca-core and
openfisca-france are both "or-later"; taking "-only" would create pointless
friction against a future upstream move to v4). Split-tree is rejected —
maintenance overhead a solo project doesn't need, protecting a hosting option
this project doesn't want. And unlicensed-forever fails the project's founding
premise: a transparency tool nobody may legally run is a contradiction.

One argument the report undersold: for *this* project §13 is not a cost, it is
the thesis. The product's signature is showing its working; a licence under
which nobody can host a closed fork of the honesty machine is the licence that
matches the mission.

Do: `LICENSE` (AGPL-3.0-or-later text), README licence section (code AGPL;
data licensing independent — EEC Licence Ouverte with attribution, ERFS
non-redistributable per D-016), `pyproject.toml` licence field, close the
licence half of D-001.

**And settle D-001's other half in the same commit**, as the report suggested,
before any firm-package code exists: the Phase 2 firm package is developed
**in-repo, as an independent extension package following OpenFisca conventions**
(YAML dated parameters, openfisca-test-format YAML cases), AGPL like everything
else, structured so it can be *offered* upstream once it has substance (IS,
C3S, CFE encoded and tested) — but not gated on OpenFisca-org governance or
review latency, which the Phase 0 audit measured as thin. Contribution is the
goal; the fork-shaped start is the schedule. Log as **D-018**.

# Addendum — 2026-09-02, after the D-025 verification cycle

## Verdict on the cycle

Endorsed in full. Two moments deserve naming because they are the hardest part
of verification done right. First, the CEBGE defence: a plausible secondary
source "correcting" the rates to 10.3 % was *refused*, by showing 10.3 % is
BOFiP's worked example of the smoothed rate at 1.55 bn — resisting a correction
takes more discipline than accepting one, and acting on it would have halved a
correct parameter. Second, the withdrawn warning written into the file *as a
withdrawal* so it cannot be re-added: that is the decision-log method operating
at the level of a single YAML comment. The corroborations (CVAE coefficients
independently re-derived down to the 0.176 %/0.175 % discontinuity; all 12 C3S
values attacked and held) are the strongest evidence the legislation layer has
had. The stationarity-hides-the-CEBGE-cliff finding is correctly filed as a
limitation; no action.

## Ruling: the firm cell table is built from files, never from agents (log as D-026)

The firm-data research is now the second measured failure of the same method:
Phase 1's six statistics agents all returned scope problems; this one returned
WRONG with 15. The fix is not a better-prompted re-run. **Calibration inputs do
not pass through an agent's prose.** The cell table is computed, by tested code,
from the primary files themselves — SIRENE stock and the ESANE tables per
docs/DATA_DOWNLOADS.md, downloaded to data/raw/ with manifest checksums —
and every number in it is reproducible by re-running the ingest on the
manifested file. Agents may be used to *locate* files and documentation, and as
adversarial verifiers of what the code computed; they may not be the source of
record for any figure. (The D-023/D-025 verifier layer stays: it is what caught
this.)

## Suggestion: grade C3S against its comparable vintage instead of declaring the bias

C3S payable in N is assessed on CA of N−1, so the model's `0.16 % × CA_N` is an
estimate of C3S payable in **N+1**. Rather than declaring "overstated by a year
of nominal growth", grade the simulated figure against receipts booked in N+1
where published (else deflate by nominal CA growth, stating the rate). One line
in reconcile converts a declared bias into a correct comparison. The formula's
declaration stays — the model still cannot do transition-year reforms of C3S.

## Standing items, fourth consecutive review

The ERFS request (Max, ten minutes, gates the only fix for the Phase 1 benefit
lines) and the git remote (CI has still never executed on a real runner). Both
survive another cycle untouched. They are now the two oldest open items in the

* The 73 unsourced files move to `data/raw/_unsourced/` (manifest entries kept,

## A diagnostic for the two red lines — offered as mechanics, not economics

Industrie +38.3 % and immobilier −70.9 % with opposite signs is the classic
signature of a **sector-perimeter mismatch between the two sources**: Ésane
classifies *profiled enterprises*, DGFiP classifies *legal units*, and an
industrial group's property or holding arm lands in different sectors under the
two conventions. Two cheap checks before any hypothesis: (1) compare the
sources on a quantity the model does not touch — firm counts or CA by sector;
if industrie/immobilier already disagree there at the same order, the residual
is perimeter, not model. (2) Decompose each red residual by size class inside
the cell table: concentrated in GE points to group/perimeter effects; uniform
across sizes points to base construction.

## Two rules promoted from lessons to standing rules

* **Mechanical before economic**: a residual gets a mechanical explanation
  attempt (and its failure recorded) before any economic hypothesis is written
  down. Binding on reviewers too — the diagnostic above is offered under it.
* **Codes, not labels**: no substring matching on French display labels
  anywhere in ingest ("IS" ∈ "ENTREPRISES"). Logic keys on codes; a test may
  enforce the absence of `in label` patterns in ingest modules.

# Addendum — verdict on the knobs increment (D-033..D-042)

## Endorsed, with the phase's most important finding named

**D-042 is the deepest thing this project has learned about verification.** The
2026 refonte *replaced* the allègements structure, so writing an old child name
succeeded — `update()` created the node, and the D-007 read-back then confirmed
the value it had itself just written. A check that shares a write path with the
thing it checks can self-confirm; read-back guarded against wrong values, not
against writing into the void. The existence-check-before-write fix is right.
Two generalisations, ruled now:

* **`update()` may never create.** Any reform write targeting a node that does
  not exist at the reform's start date is an error by default — creation is a
  separate, explicit operation. This subsumes the existence check and closes
  the whole class, not the instance.
* **A verification is only as good as its causal independence.** Where
  possible, read-backs compare against an *independently constructed*
  expectation (the spec value, a fresh parameter resolution), not against
  whatever the write path now contains. Audit the other verify_* functions for
  the same shared-path pattern once; record what is found either way.

## The 17.7 bn / zero-cost bug gets a structural answer: double-entry (rule, log it)

`reform_cost` being household-side only was caught by the behavioural layer by
luck of adjacency. The structural guard is an **accounting identity asserted on
every reform run**: the deltas across sectors must balance — what households
and firms gain, the state loses, to stated tolerance. A reform that moves
labour cost by 17.7 bn with a public cost of exactly zero should die on the
identity, not wait for a reviewer. Cheap, vectorised, and it catches every
future knob whose cost wiring is incomplete on either side.

## The +107 % cliff finding becomes a runtime flag, not just a decision entry

The barème/+10 % vs cliffs/+107 % contrast upgrades D-015 from "level shift"
to "mis-shaped density", and it has a product consequence: compute, per reform,
the **share of mechanical yield concentrated in narrow wage bands** (households
within a small window of the instrument's thresholds). Above a threshold share,
the UI carries the specific caveat — *"this reform's yield turns on a narrow
wage band, where the synthetic distribution is least reliable (D-015); treat
the level as overstated until the ERFS population lands."* The backtest
measured the failure mode; the runtime should point at it whenever a user walks
into it.

## C4's resolution is exemplary

Bounds read from the tables, straddling zero because the paper's own
comparisons disagree, with the authors' "grande prudence" carried into the
parameter file. That is what "no detectable response" looks like when it is
sourced rather than assumed.

## The 23-minute suite — tier it before it compounds

Chiffrage cases that touch only IR/cotisation instruments do not need the
full benefits cascade: run them light-tier where the article's instruments
permit, and mark the genuinely full-tier ones. Split the suite with pytest
marks: a fast default gate (target < 5 min) and the full pass (nightly, or on
CI where minutes are cheap). Do not let local test pain create pressure to
skip runs — that is how green suites rot.
