# Phase 1 — Synthetic Population + Distributional Engine: Implementation Specification

**Project**: Impôts · **Phase**: 1 of 4 · **Prerequisite**: Phase 0 as built (90 tests green, D-000…D-010 on record)
**Audience**: the implementing agent. Everything marked **[VERIFIED]** was executed against `openfisca-france 176.0.8` / `openfisca-core 44.7.0` on 2026-08-28 in a live environment — including the population-scale patterns, which surfaced two silent-failure modes you must not rediscover the hard way (§1). One thing could **not** be verified remotely (the EEC file's household identifier, §3) because INSEE file downloads are blocked from the authoring environment; it is handled as an explicit decision gate you resolve in milestone M0 on the development machine, where the download works normally.
**This spec is written against the as-built Phase 0**, not the Phase 0 spec: it assumes `engine/{system,situations,outputs,reforms,compute}.py` with their current exports, `ReformSpec` as implemented, `verify_bareme`, tri-state `parent_isole`, and the `historique_revenus` flag of D-005.

---

## 0. What Phase 1 is

Any household reform, priced for the country: **aggregate revenue effect** and **winners/losers by decile of niveau de vie**, computed over a calibrated synthetic population built entirely from open data — with a **published reconciliation report** showing exactly how far the synthetic population's simulated aggregates sit from the real published totals. The reconciliation table is not an internal QA artefact; it is a first-class product output and the project's credibility page.

**Definition of done**:
1. `impots population build` (CLI) produces `data/processed/population_{vintage}.parquet` from raw open data, deterministically (fixed seed), with a manifest of input checksums.
2. `impots population run --reform reform.json` produces weighted aggregate + decile results; a run with no reform reproduces the pinned baseline aggregates (golden population test).
3. `reports/reconciliation.md` is generated by code, shows simulated-vs-published for every line in §5, and no line's residual is silently omitted.
4. `POST /population/simulate` answers a quick-tier reform request; the UI's population tab shows aggregate cost + a decile chart + the L1 fidelity banner.
5. All Phase 0 tests still green; new population tests green; CI green without network access (fixture sample, §7).
6. The three §0.5 pre-flight items are done and logged.

**Out of scope for Phase 1** (refuse, even if easy): firms (Phase 2), any behavioural response (Phase 3), indirect taxes, pensions/dynamics, capital income and the top tail (explicitly disclaimed in-product, §4.2), local taxes, non-metropolitan special regimes beyond what EEC covers.

## 1. Population-scale OpenFisca — the verified mechanics **[VERIFIED]**

This section is load-bearing. Two of its findings fail **silently or fatally** if ignored.

### 1.1 The vectorised builder pattern

```python
import numpy as np
from openfisca_core.simulation_builder import SimulationBuilder
from impots.engine.system import baseline   # or reformed_for(spec, year)

ROLE = {"foyer_fiscal": "declarant_principal",
        "famille": "demandeur",
        "menage": "personne_de_reference"}   # see 1.2 — these exact strings

def build_sim(tbs, n_persons, person_group_id, roles_by_entity, inputs):
    sb = SimulationBuilder()
    sb.create_entities(tbs)                      # REQUIRED before declare_*
    sb.declare_person_entity("individu", np.arange(n_persons))
    for ent in ("foyer_fiscal", "famille", "menage"):
        inst = sb.declare_entity(ent, group_ids[ent])          # one id per group
        sb.join_with_persons(inst, person_group_id[ent],       # person -> group id
                             roles_by_entity[ent])             # person -> subrole key
    sim = sb.build(tbs)
    for (var, period), arr in inputs.items():
        sim.set_input(var, period, arr)          # numpy arrays; enums as string arrays
    return sim
```

Measured **[VERIFIED]** (container, one core class of hardware — treat as ratios, not promises):
- build at N=100 000 single-adult households: **0.2 s**
- `impot_revenu_restant_a_payer` at N=100 000: **~20 s**, RSS ~2.3 GB
- full cascade (`revenu_disponible`) at N=10 000 with 3-year inputs: **~13 s** → budget **minutes, not seconds**, for a full-tier 100 k run
- monthly variables cost ~12 `set_input` calls per variable-year; that is fine

**Product consequence**: population runs are **batch jobs** (CLI writes parquet; API/UI read results), except a bounded "quick" tier (§6). Do not put a 100 k full-tier run behind a synchronous HTTP request.

### 1.2 Silent-failure mode #1: roles are *flattened subrole* keys

`join_with_persons` matches each role string against `entity.flattened_roles` — the **subroles**. The intuitive role names from the JSON path (`declarant`, `parent`) match **nothing**, and the failure is a *silent wrong answer*: every person gets a null role, `nbptr` computes **0.0** for every foyer, IR is garbage, and **no exception is raised** **[VERIFIED]**. The valid keys:

| Entity | Flattened subrole keys |
|---|---|
| foyer_fiscal | `declarant_principal`, `conjoint`, `personne_a_charge` |
| famille | `demandeur`, `conjoint`, `enfant` |
| menage | `personne_de_reference`, `conjoint`, `enfant`, `autre` |

**Mandatory guard** in the runner, after every build: `assert nbptr.min() >= 1` (and `af`-relevant runs: children counts consistent). This class of bug — plausible numbers, no error — is the project's named worst failure (see D-007); the guard is not optional.

### 1.3 Fatal-failure mode #2: enum defaults crash vectorised parameter lookups

With `zone_apl` left at its default (`non_renseigne`), the aides_logement formulas index the parameter tree by the enum value and raise `ParameterNotFoundError: ...l_plafonds_loyers.par_zone[non_renseigne]` **[VERIFIED]**. And because benefit reference periods look back (D-005), setting year N alone is not enough: the lookback months of **N-1 and N-2** must also be set **[VERIFIED — the crash persisted with year-N-only inputs and disappeared with 3-year inputs]**.

Rule: for every population run, set for **all 36 months of N-2..N**: `salaire_de_base`, `zone_apl`, `statut_occupation_logement`, `loyer` (renters; 0 for owners). Phase 1 assumes steady state (year N values replicated backwards) — same assumption as `historique_revenus`, now the only mode.

### 1.4 Expected noise, and the assertion that separates noise from failure

All-population runs hit formula edge cases (zero incomes) and emit `RuntimeWarning: divide by zero` from `ir.py` — benign **[VERIFIED: with correct roles, NaN count = 0 at 100 k]**. The guard is: **assert `np.isnan(result).sum() == 0`** on every output array. NaNs mean a wiring bug (that is how the role bug first surfaced), never acceptable output.

`scripts/verify_population_engine.py` (shipped alongside this spec) encodes 1.1–1.4 as a runnable gate: single-adult synthetic population, N=10 k, asserts roles/nbptr/NaN/aggregate-tax-ratio. Run it before and after any change to the runner. **[VERIFIED green as shipped: aggregate IR = 5.9 % of gross wages on the lognormal test population]**

## 3. Milestone M0 — reconnaissance gate (resolves the one unverified fact)

Write and run `scripts/verify_eec.py` against the real FD before any pipeline code:

1. row count == 353 420; 83 columns; `EXTRIAN` present, > 0, and `EXTRIAN.sum()` within 10 % of the French 15+ population (~54–56 M — record the actual number);
2. inventory: print every column with its Varmod label;
3. **the gate**: does any column group individuals into households (IDENT/IDMEN/IDLOG-like)? and which wage/income variables exist (SALRED/SALMEE-like, monthly or annual, net or gross)?

Then branch — the *downstream interface is identical in all branches* (§4.1's parquet schema), so only `skeleton.py` differs:

- **Branch A — household id exists**: group directly; households are real. Best case.
- **Branch B — no household id** (likely for the open FD): assemble synthetic households from the FD's household-composition summary variables (type de ménage, couple status, children counts) + source 5 margins: pair adults and attach children by matching the joint distribution (household type × age band × region). Log the assembly algorithm as a decision; it is an explicit L1 fidelity cost, stated in the UI banner.
- **Branch C — the affiliation unlock**: if a live academic affiliation is available, the **ERFS fichier détail via Quetelet-Progedo** (free, signed agreement, 2–6 weeks) replaces the skeleton with *real households carrying real incomes* and collapses most of §4.2's imputation. This decision belongs to Max, now — the answer changes ~a month of work. Ask; do not assume either way.

M0 output: `docs/M0_RECON.md` with the findings, the chosen branch, and the branch's known costs. **Design freeze for §4 happens only after M0.**

## 4. The pipeline (`src/impots/population/`)

### 4.1 The interface every stage codes against

`data/processed/population_{vintage}.parquet` — one row per **person**:

```
person_id, household_id, weight,
age, sex, region,
role_menage, role_foyer, role_famille,          # subrole keys, §1.2 vocabulary
salaire_brut_annuel,                            # >= 0
statut_activite,                                # employed / unemployed / retired / inactive / student
pension_annuelle, chomage_annuel,               # v1 imputed, see 4.2
statut_occupation, loyer_mensuel, zone_apl      # menage-level, replicated per person
```

Weights live in this file and in aggregation — **never inside OpenFisca**.

### 4.2 `skeleton.py` + `incomes.py`

Skeleton per M0 branch. Incomes, v1 discipline:
- Wages: EEC wage variable where present; where absent/banded, hot-deck imputation within age×sex×CS×region strata (QRF is a v2 upgrade, not v1).
- Unemployment benefit & pensions: impute from status via published aggregate distributions (DREES/UNEDIC), acknowledged **LOW fidelity**.
- **No capital income in v1.** Consequence, stated verbatim in the UI and reconciliation report: *the top of the distribution is wrong; nothing above the ~95th percentile is publishable*. (CSG on capital, PFU, IFI: absent. This is the honest cost of open data — real income microdata via branch C would shrink it, and since D-096 that unlock is a door far away rather than a queue. F1b tests whether published tranche-level statistics can open part of it without microdata.)

### 4.3 `calibrate.py` — raking, with a hard epistemic rule

Implement classic raking (IPF) directly (~80 lines, no dependency): iterate proportional fitting of `weight` over margin sets until relative change < 1e-6 or 200 iters; bound final weight ratios to [0.2, 5] × initial; convergence + bounds are test-asserted.

Margins (v1, keep modest): (a) individuals by age band × sex (national); (b) households by type (source 5); (c) wage earners by wage decile + total wage bill (sources 2 & 4).

**The rule**: anything used as a calibration margin is thereby *spent* and cannot appear as a validation line. IR totals, benefit totals (source 3, 6) are **validation only** — the reconciliation table's value is exactly that the model was not tuned to it. This rule is stated in the reconciliation report itself.

### 4.4 `to_openfisca.py` + `runner.py`

`to_openfisca.py`: parquet → the §1.1 builder. Group ids from `household_id` (menage) and derived foyer/famille ids (v1: one foyer + one famille per ménage; couples per FD; log the simplification). 36-month inputs per §1.3. `parent_isole` inference: reuse engine's D-006 logic — lone adult + children ⇒ `caseT` true.

`runner.py`:
```python
def run(population_parquet, year, reform: ReformSpec | None, tier, sample: int | None) -> ResultsFrame
```
- baseline TBS via `system.baseline()`, reform via `system.reformed_for()` (inherits cache + `verify_bareme`);
- guards after every run: `nbptr.min() >= 1`, NaN count 0, timing logged;
- `sample=N`: deterministic weighted subsample (fixed seed) with weights rescaled — the quick tier;
- output: per-household results parquet (registry keys × baseline/reform), written to `data/processed/runs/`.

### 4.5 `aggregate.py`

Weighted: total per instrument (IR, CSG-on-wages, cotisations, each benefit, revenu disponible); **deciles of niveau de vie** = ménage `revenu_disponible` / consumption units (OECD-modified: 1 + 0.5·(adults−1) + 0.3·children<14 — implement and unit-test); per decile: mean Δ, share winners / losers / unaffected (|Δ| < 10 €); an overall aggregate cost of the reform. Present exactly these; resist adding a top-1 % row (§4.2).

## 5. Reconciliation report (`reports/reconciliation.md`, generated)

One table, generated by `impots population reconcile`, committed with each population vintage:

| Line | Simulated | Published | Residual | Source | Status |
|---|---|---|---|---|---|
| Wage bill | … | … | % | URSSAF | *calibrated* (spent) |
| IR total yield | … | … | % | Voies et Moyens | validation |
| Foyers imposés (count) | … | … | % | DGFiP | validation |
| CSG activité | … | … | % | comptes Sécu | validation |
| AF / PPA / RSA / AL totals | … | … | % | CNAF/DREES | validation |

Tolerances to *declare* (not to silently pass): wage bill ±2 % (calibrated); IR ±10 %; benefits ±25 % — benefits will run high because OpenFisca assumes 100 % take-up while real non-take-up is large (RSA-class benefits: roughly a third unclaimed per DREES — cite the current DREES estimate in the report, do not hardcode this one). If IR misses by more than 10 %, the population is not ready to ship; find out why (usually: top-tail wage imputation or missing income categories) before proceeding to §6.

Golden population tests: with the pinned data vintage + seed, aggregate IR, wage bill, decile shares are asserted to the euro (they are deterministic). Any change to pipeline code that moves them must move the pins in the same commit with a decision-log entry — D-004's policy, extended to Phase 1.

## 6. API + UI

**API**: `POST /population/simulate` — `{reform: ReformSpec, year, tier: "quick"}`: quick tier only over HTTP (deterministic ~20 k-household subsample; budget < 90 s; return the sampling note in the payload). Full runs: CLI only in Phase 1. `GET /population/baseline` serves the precomputed baseline aggregates + decile table + reconciliation summary + population vintage metadata. Extend `schemas.py`; keep Phase 0 endpoints untouched.

**UI**: a second tab, "Population". Shows: aggregate cost of the current reform (with the quick-tier sampling caveat), the decile winners/losers chart, and the **L1 banner**: population is synthetic, built from open data, calibrated to X/Y/Z, top of the distribution excluded, link to the reconciliation report; states the vintage. Chart: keep it to one horizontal bar chart (mean Δ by decile, winners/losers split); follow the repo's existing UI conventions (single file, no build step). D-005's transparency rule carries over: the tab says which population vintage and which tier produced every number on screen.
